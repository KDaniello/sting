# API

Каждый контракт, пересекающий границу: сквозные типы, три командные строки, протокол HTTP, форматы
вывода и коды диагностики. Как устроено дерево — [`ARCHITECTURE.md`](./ARCHITECTURE.md). Чем это
доказано — [`TESTING.md`](./TESTING.md).

Всё ниже считано с настоящих сигнатур в `crates/`, включая неудобные детали.

## 1. Сквозные типы

### 1.1 `Finding` — единица результата security-контура

```rust
pub struct Finding {
    pub detector_id: DetectorId,                          // &'static str, а не enum — см. ниже
    pub severity: Severity,                               // Info < Low < Medium < High < Critical
    pub message: String,                                  // что не так, в терминах этого кода
    pub remediation: String,                              // что менять — обязательное поле
    pub location: Location,                               // файл, строка и колонка, 1-индексированные
    pub confidence: Option<Confidence>,                   // Some только после прохода скоринга
    pub dynamic_verification: Option<DynamicVerification>,// Some только после прохода моста
    pub suggestion: Option<Suggestion>,                   // машинно-применимая правка, §1.4
}
```

**`remediation` обязательно, а не факультативно.** Разделение с `message` намеренное: `message`
объясняет дефект, `remediation` говорит разработчику, что менять, — та же пара, что `error:` и
`help:` у `rustc`. В SARIF уходит двумя штатными каналами: `properties.remediation` на каждом
результате и `ReportingDescriptor.help` на каждом правиле.

**`detector_id` — строка, а не `DefectClass`.** Таксономия TONScanner есть выбранный стартовый скоуп,
а не потолок: `EPS` и `UDA` — настоящие зарегистрированные детекторы, которых в `DefectClass` нет
вовсе, а `DEPR` не про уязвимости. Ограничение идентификатора перечислением сделало бы их
невыразимыми. `Finding::defect_class()` восстанавливает класс там, где он есть.

**Отдельного поля `id` нет.** Бенчмарк сопоставляет находки с эталоном по
`(file, detector_id, line_range)`, и этот кортеж уже определяет находку однозначно. `stable_id()`
собирает ключ дедупликации по требованию.

### 1.2 Отказ и неопределённость выражены типом

```rust
pub enum DynamicVerification {
    Confirmed(ProofOfConcept),  // эмулятор воспроизвёл предсказанное поведение
    Refuted,                    // паттерн совпал, поведение безопасно
    Inconclusive(String),       // проверить нельзя, и вот почему
}

pub struct ProofOfConcept {
    pub expected: String,       // что предсказал статический проход
    pub actual: String,         // что наблюдал эмулятор
    pub steps: Vec<String>,     // достаточно, чтобы человек повторил вручную
}
```

`Refuted` **не удаляет** находку: отчёт понижает её отрендеренную важность. Разница существенна —
удаление скрыло бы от пользователя и то, что паттерн в коде есть, и то, что он был проверен.

`Inconclusive` несёт причину строкой, потому что причин много и они содержательны. Подтверждённый
пример: находки, завязанные на `in.senderAddress`, недостижимы через
`TvmEmulator::send_internal_message` в принципе — записано, а не переодето в `Refuted`.

Тот же принцип в двух других контурах:

| Тип | Крейт | Что выражает |
|---|---|---|
| `ProbeOutcome::PrecompiledContractUnsupported` | `sting-scamcheck` | байткод зарегистрирован в `ConfigParam 45` и под эмулятором не исполняется вовсе |
| `ProbeOutcome::ExecutedSilently` | `sting-scamcheck` | успех, `exit_code = 0` и ноль исходящих действий — принял и проглотил |
| `MatchStatus` | `sting-abi-registry` | совпал ли пересобранный байткод с ончейн-кодом |
| `ExtractionTier::Heuristic` с обязательным `confidence` | `sting-abi-core` | схема получена эвристикой, а не компилятором |

### 1.3 `Confidence` — диапазон, гарантированный конструктором

```rust
Confidence::new(f32) -> Result<Confidence, ConfidenceRangeError>  // отвергает вне [0,1] и NaN
Confidence::saturating(f32) -> Confidence                          // клампит; NaN становится 0.0
```

Два конструктора не дублируют друг друга. `new` — для внешнего или непроверенного входа.
`saturating` — для вызывающего, чьё значение ограничено **по построению** (взвешенная сумма, где
каждое слагаемое уже в диапазоне, а веса дают 1.0) и который всё же хочет защиты от краевого случая
плавающей точки без `Result`, использованным которого не ожидает увидеть ни одна сторона.

### 1.4 `Suggestion` — машинно-применимая правка, и почему её почти ни у кого нет

```rust
pub struct Suggestion { pub start_byte: usize, pub end_byte: usize, pub replacement: String }
```

**Заполняют её ровно два детектора: `DEPR` и `SUA`.** Это граница, а не недоделка.

Находка, починка которой требует человеческого суждения о намерении, не имеет права нести
`Suggestion`: какую проверку добавить, какая переменная имелась в виду, было ли затенение осознанным.
Правдоподобно выглядящая неверная проверка, вставленная автоматически, хуже отсутствия находки, ибо
производит ощущение решённой задачи. Устаревшее имя из stdlib и `x =+ 1`, написанное вместо `x += 1`,
— единственные два случая, где существует одна детерминированная верная замена. Ровно ту же черту
проводят `cargo fix` и `clippy --fix`.

### 1.5 `ContractSchema` — единица результата abi-layer

```rust
pub struct ContractSchema {
    pub ir_schema_version: String,          // версия ЭТОЙ схемы, а не компилятора-источника
    pub source_language: SourceLanguage,    // tolk | tact | func
    pub extraction_tier: ExtractionTier,    // compiled | heuristic | statistical
    pub contract_name: Option<String>,
    pub metadata: ContractMetadata,         // author, version, description из заголовка
    pub storage: Option<TypeRef>,           // None — настоящее значение, а не заглушка
    pub types: Vec<NamedType>,              // дедуплицированная таблица; остальные поля индексируют в неё
    pub incoming_internal: Vec<MessageRef>,
    pub incoming_external: Vec<MessageRef>,
    pub outgoing: Vec<MessageRef>,
    pub get_methods: Vec<GetMethod>,
    pub errors: Vec<ErrorCode>,
    pub confidence: Option<ExtractionConfidence>,   // Some тогда и только тогда, когда tier = heuristic
    pub field_confidence: Option<FieldConfidence>,  // разбивка по категориям, опциональна и для Tier 2
}
```

**Всё индексирует в `types[]` и никогда по имени.** Иначе два разных типа с одинаковым именем из
разных файлов слились бы молча.

**`storage: None` — настоящее значение, а не «ещё не извлекли».** Проект без заголовка `contract{}`
компилируется Tolk'ом и действительно не имеет объявленного типа storage.

**Один кросс-полевой инвариант** — `confidence` заполнен тогда и только тогда, когда
`extraction_tier == Heuristic` — не обеспечен конструктором, потому что это plain-data с публичными
полями, и проверяется явным `validate()`, который каждый экстрактор зовёт перед возвратом. Крейт не
делает этого за них: структура с публичными полями не может отказаться быть построенной в невалидном
состоянии.

**`ir_schema_version` движется независимо** от `abi_schema_version` у Tolk и от версии `ContractABI`
у Tact. Поднималась однажды, когда в схему добавился `TypeShape::Str`: оба языка этот вид эмитят,
модели для него не было, и любое строковое поле молча деградировало в `Unknown`.

## 2. `sting` — security CLI

```
sting <COMMAND>
  -v, -vv                 debug / trace (RUST_LOG перебивает целиком)
  --color auto|always|never
```

| Команда | Что делает | Ключевые флаги |
|---|---|---|
| `lint <path>` | прогоняет детекторы по файлу или каталогу | `--format human\|sarif\|json`, `--output`, `--config`, `--min-severity`, `--fix` |
| `scan <address>` | динамический разбор задеплоенного контракта | `--get-method` (повторяемый), `--testnet`, `--force-refresh`, `--format`, `--output` |
| `verify <path> <address>` | замыкает статику на динамику: линт, гипотеза, эмулятор, скоринг | `--hypotheses <file.toml>` (обязателен), `--baseline`, `--min-severity` |
| `bench` | precision и recall по размеченному корпусу | `--corpus`, `--report`, `--baseline`, `--update-baseline` |
| `fetch <address>` | скачивает code и data по ончейн-адресу | `--out`, `--testnet`, `--force-refresh` |
| `explain <detector_id>` | профиль детектора: что ищет, какая у него замеренная точность, где границы | — |
| `config dump` | эффективная конфигурация после слияния дефолтов и файла | `--config` |
| `doctor` | четыре версии, от которых зависит ответ: эмулятор, глобальная версия, компилятор, грамматика | — |
| `fuzz <target>` | тонкая обёртка над `cargo fuzz run`, а не реализация | `--time`, `-- <libFuzzer args>` |

### 2.1 Три вещи, которых эти команды намеренно не делают

**`fetch` не даёт исходника.** Он скачивает байткод. У задеплоенного контракта нет восстановимого
через эту команду исходника: то, что приносит `fetch`, есть вход для эмулятора и фаззера, но никогда
для статических детекторов. Если у вас есть и исходник, и собственная задеплоенная копия, вы
передаёте `.tolk` в `lint`, а адрес в `fetch` **раздельно**; `sting` никогда не компилирует одно в
другое.

**`scan` не запускает детекторов и не зовёт динамический мост.** У адреса нет исходника, значит нет
`Finding`, из которого строится гипотеза, а выведение гипотезы из одного байткода не предпринимается:
это открыто нерешённая исследовательская задача — общее восстановление конвенции диспетчеризации
сообщений, — а не срезанный угол.

**`verify` не выводит гипотезу из исходника.** `--hypotheses` — это TOML, написанный человеком,
который уже знает ответ, по секции на класс дефекта. Находка, класс которой файл не покрывает, всё
равно попадает в отчёт и всё равно скорится, на одной статической очевидности, ровно как в `lint`.

### 2.2 Коды возврата и одна настоящая дыра

| Ситуация | Код |
|---|---|
| успех | `0` |
| ошибка исполнения: нет файлов, битый конфиг, сеть | `1` |
| `scan` нашёл хотя бы одну находку | `1` |
| `doctor` не смог прочесть одну из четырёх версий | `1` |
| **`lint` нашёл хотя бы одну находку** | **`0`** |

Последняя строка — **настоящий дефект интеграции, а не дизайн**. `sting lint` возвращает `0`,
сколько бы находок ни выдал, потому что ни один путь его ветки не завершается ошибкой. Линтер,
всегда возвращающий ноль, не может гейтить чужой CI: самый очевидный способ им пользоваться сегодня
не работает без обвязки, разбирающей SARIF. Устранение — флаг `--fail-on <severity>`, и он назван
здесь, а не спрятан.

### 2.3 Форматы вывода

**`human`** — больше, чем `file:line:col: [ID] Severity: message`. Под координатной строкой печатается
строка исходника с `^^^^^` под точным диапазоном колонок и всегда строка `= help: {remediation}`.
Сниппет пропускается, когда `Location.file` физически нечитаем в момент рендера: находки `scan`
используют сам адрес как `file`, и читать нечего.

**`sarif`** — SARIF 2.1.0 через `serde-sarif`, а не собранный руками JSON.
`tool.driver.name = "sting"`, `ruleId` — `sting/<CODE>`. Каждый результат несёт
`properties.confidence` и `properties.dynamicVerification`
(`confirmed`/`refuted`/`inconclusive`/`not-attempted`). Вывод проверяется против настоящей
JSON-схемы SARIF 2.1.0 в тесте, а не считается корректным на том основании, что структура
типизирована.

**`json`** — плоский массив находок, не SARIF: отдельный формат для потребителя, которому обвязка
SARIF не нужна.

**Как выбирается умолчание**: явный `--format` побеждает; иначе `sarif`, когда задан `--output`;
иначе `human` на интерактивном терминале; иначе `sarif`.

**Чистота stdout — инвариант.** Статусные строки `scan` печатаются только тогда, когда формат
разрешился в `human`. Безусловная их печать однажды вклинила обычный текст перед JSON-нагрузкой и
испортила её для любого парсера ниже по течению — найдено реальным прогоном, а не ревью.

### 2.4 `Sting.toml`

```toml
[detectors]
enable = ["GVR", "LEP"]     # непустой список работает как whitelist
disable = ["ID"]            # всегда вычитается

min_severity = "high"       # необязательный глобальный пол

[[suppressions.rule]]
detector = "LEP"
file = "contracts/legacy.tolk"
line = 42
reason = "обёрнуто внешней библиотекой, end_parse зовёт вызывающая сторона"
```

Файл ищется вверх по дереву от текущего каталога — та же конвенция, что у `Cargo.toml` и
`Acton.toml`.

**Все четыре поля подавления обязательны, включая `reason`.** Сопоставимый механизм у Misti причины
не требует. Необъяснённое подавление есть ровно тот класс стареющих неподотчётных исключений, который
этот механизм должен делать труднее, а не легче. Инлайновый эквивалент — `// sting:allow(ID1,ID2)
причина` на строке непосредственно перед находкой, и строка **без причины подавлением не признаётся
вовсе**: находка остаётся видимой. Неиспользованные правила дают предупреждение.

**Коды детекторов проверяются не в `sting-core`.** `StingConfig::parse` — чисто структурный разбор:
`sting-core` не зависит от `sting-detectors` и не может знать вселенную валидных идентификаторов.
Проверка живёт там, где известен зарегистрированный набор. Обратное однажды было реализовано и
оказалось дефектом: конфиг отвергал легитимный не-таксономический идентификатор — найдено прогоном
`sting config dump`, а не тестом.

**Спроектировано и без потребителя**: `[detectors.rules.<ID>].severity_override`, `[corpus]`,
`[report]`. Перечислено здесь честно, а не выдано за работающее.

## 3. `abi-layer` — CLI извлечения

| Команда | Что делает |
|---|---|
| `extract <path>` | нормализованный `ContractSchema` из одной точки входа. `--lang tolk\|tact\|func` перебивает определение по расширению |
| `bench` | Tier 1 — структурная полнота, Tier 2 — precision и recall, плюс пропускная способность против реального корпуса |
| `dictionary-build` | пересобирает словарь method id по всему реальному корпусу Tolk, Tact и FunC |
| `dictionary-probe <address>` | зовёт каждый известный method id на реальных ончейн-code и data — **исходник не читается вовсе** |
| `dictionary-verify` | пересобирает словарь во временный файл и сравнивает с закреплённым байт в байт |
| `dictionary-audit --sample <n>` | перекомпилирует выборку записей, полученных от компилятора, и сверяет её с собственным `abi.json` tolk |
| `catalogue-fetch --checkout <clone>` | перечитывает два списка `ton-blockchain/abis` из рабочей копии, коммит берётся из неё самой |
| `catalogue-diff` | различие с этим каталогом в обе стороны ([`domains/method-dictionary.md`](./domains/method-dictionary.md) §10) |
| `decode --body <base64>` / `--hash <tx>` | что за операция в сообщении и с какими полями ([`domains/decode.md`](./domains/decode.md)) |
| `decode-sample --transactions <n>` | сколько реального трафика mainnet читается датасетами, тремя долями |
| `catalogue-operations --checkout <clone>` | словарь операций, выученный по файлам типов каталога фонда |
| `sweep --db <sqlite>` | обход mainnet, дедуплицированный по хешу кода, с пробой каждого нового кода |
| `coverage-report --db <sqlite>` | агрегатное покрытие плюс лучшие кандидаты на расширение словаря |
| `tact-share --db <sqlite>` | сколько уникальных ончейн-кодов объявляют себя Tact ([`domains/method-dictionary.md`](./domains/method-dictionary.md) §8) |

**`--format tlb` зарезервирован и не реализован** — заявлен в дизайне схемы, потребителя нет.

**`sweep` создаёт настоящую устойчивую нагрузку на публичный сторонний сервис.** `--pilot-size` по
умолчанию 5000; прежде чем выходить за пилотный размер, читается [`DATA.md`](./DATA.md) §4.

**`--reprobe` появился по факту найденного пробела**, а не по дизайну: словарь, выросший **после**
первой пробы кода, второго шанса на этот код не получал, потому что уже пробованный код повторно не
рассматривался. Флаг перепроверяет ранее нераспознанные коды и не трогает распознанные.

## 4. `sting-abi-service` — HTTP

Единственный контейнеризованный контур. `axum` и `tokio`; компиляция уезжает в блокирующий пул, а
батч внутри него параллелится через `rayon`.

| Метод | Путь | Лимит частоты | Что делает |
|---|---|---|---|
| `POST` | `/v1/extract` | да | схема из одного присланного исходника |
| `POST` | `/v1/extract/batch` | да | до `batch_max_items` за запрос |
| `POST` | `/v1/verify` | да | сверяет пересобранный байткод с ончейн-кодом по адресу |
| `POST` | `/v1/probe` | да | проба method id по адресу, без исходника |
| `POST` | `/v1/decode` | да | что за сообщение — по хешу транзакции или по телу ([`domains/decode.md`](./domains/decode.md)) |
| `GET` | `/v1/schema/{address}` | нет | ранее верифицированная схема из хранилища |
| `GET` | `/v1/health` | нет | живость |
| `GET` | `/v1/version` | нет | версия сервиса и схемы |

**Разделение на два под-роутера намеренно**: лимит частоты применяется к путям извлечения и никогда к
`/v1/health` и `/v1/version` — иначе система мониторинга лишилась бы возможности опрашивать сервис
ровно тогда, когда он под нагрузкой.

### 4.1 Одна форма ошибки

Каждый неуспешный ответ — `{"error": {"code": "…", "message": "…"}}`, включая битое тело и
превышение размера: собственные тела отказа фреймворка не протекают наружу неструктурированными.

| Код | HTTP | Смысл |
|---|---|---|
| `invalid_request` | 400 | битый JSON, неизвестный `lang`, слишком большой батч — ошибка клиента |
| `unsupported_language` | 400 | под этот язык не зарегистрирован экстрактор |
| `compilation_failed` | 400 | компилятор отработал и выдал настоящую ошибку компиляции |
| `payload_too_large` | 413 | тело больше `max_body_bytes` |
| `rate_limited` | 429 | этот адрес израсходовал бюджет |
| `timeout` | 504 | извлечение не уложилось в бюджет |
| `no_verified_source` | 404 | для адреса нет верифицированного исходника — честная ошибка, **никогда пустой `200`** |
| `on_chain_resolution_failed` | 502 | сбой апстрима либо адреса не существует |
| `registry_unavailable` / `tier3_unavailable` | 503 | подсистема не сконфигурирована на этом развёртывании — пробел деплоя, а не плохой запрос |
| `decode_unavailable` | 503 | на этом развёртывании нет датасета операций — тот же пробел развёртывания, что и двумя строками выше |
| `unauthorized` | 401 | развёртывание называет ключи, а запрос не предъявил ключа либо предъявил неизвестный |
| `quota_exhausted` | 429 | ключ известен и исчерпал бюджет периода — это **не** тот же отказ, что `rate_limited` |
| `result_too_large` | 507 | ответ больше `max_result_bytes`, и он отвергается, а не урезается |
| `internal_error` | 500 | наш дефект; клиент получает общий текст, внутренние пути и состояние не утекают |

**Не знать — не ошибка.** `POST /v1/decode` отвечает на опкод, которого никто не называет, кодом
`200` и полем `unknown: true`. `404` сказал бы вызывающему, что неверен его вопрос, тогда как кончилось
знание этой платформы, — и спрятал бы в код ошибки долю, которой продукт измеряется.

**`rate_limited` и `quota_exhausted` — два лимита, а не один.** Первый ограничивает всплеск с одного
адреса, второй — период для одного вызывающего, с какого бы числа адресов он ни приходил. Вызывающий,
которому сказали только `429`, не отличит «сбавь темп» от «приходи завтра».

**Различение `invalid_request` и `internal_error` — не педантизм.** `internal_error` означает «наш
дефект», и переиспользование его для ошибки клиента вводило бы в заблуждение того, кто читает логи,
систематически.

### 4.2 Три независимых лимита, а не один

```rust
max_body_bytes:      1_000_000
compile_timeout:     60s        // убивает подпроцесс компилятора — настоящее принуждение
request_timeout:     90s        // = compile_timeout + 30 с запаса
batch_max_items:     100
max_result_bytes:    1_000_000  // сколько сервис вправе вернуть
rate_limit:          60 запросов / 60 секунд на адрес
quota:               10 000 запросов / 24 часа на ключ, когда ключи названы
```

**Размер результата — третий лимит, и ни один из двух других его не заменяет.** Маленький запрос,
отвеченный быстро, всё ещё может назвать сообщение, чтение которого длинно, а вызывающий, просивший
декодирование, не просил мегабайта. Сверх лимита запрос падает с `result_too_large`, а не отвечается
обрезанным чтением, выглядящим целым.

**Ключи — решение развёртывания.** Пустой `STING_API_KEYS` оставляет сервис открытым, каким он и был
с самого начала; названные ключи включают разом и проверку ключа, и квоту, ибо необязательный ключ —
это ключ, который дешевле не предъявлять.

`compile_timeout` и `request_timeout` — **отдельные поля, а не одно, выведенное из другого**. Первое
убивает процесс компилятора и освобождает блокирующий поток; второе — асинхронная страховка на
случай, если этот механизм не вернётся, и единственная граница для батча, чью суммарную длительность
поштучный таймаут не ограничивает.

**60 и 90 выбраны не на глаз.** Первый нагрузочный прогон, на 20 и 25, показал, что батч из **трёх**
контрактов Tact устойчиво ловил `504`. Дело не в раутинге: параллелизм работал, контейнер доходил до
550% CPU. Бюджет был откалиброван без настоящей стоимости холодного старта `tact.js` под
конкуренцией, p99 около 11.8 секунды на один вызов. Нынешние числа взяты из второго прогона, где все
запросы завершились `200`.

**Оставшаяся оговорка**: эти умолчания проверены при размере батча около трёх, а не при полной сотне
под конкуренцией. Отчёт с новыми умолчаниями не переигрывался, и пункт остаётся открытым.

## 5. `sting-scamcheck` — рисковые сигналы

Два бинаря в одном крейте.

```
sting-scamcheck <адрес-жетона>
gift_trust_check <адрес-коллекции-или-предмета> [--domain X] [--wallet Y]
```

Обоим нужен настоящий `libemulator` через `STING_LIBEMULATOR_PATH`.

### 5.1 Композитный скоринг, а не однофакторный вердикт

```rust
pub struct ScamCheckReport {
    pub mint_rights_renounced: Option<bool>,  // из get_jetton_data(): admin_address == addr_none
    pub honeypot_reverted: Option<bool>,      // проба перевода на НАСТОЯЩИХ держателях
    pub top_holders_share: Option<f64>,       // концентрация выпуска
    pub lp_owner_share: Option<f64>,          // доля владельца в пуле ликвидности
}
```

| Сигнал | Очки |
|---|---|
| права минта не отозваны | 1 |
| проба перевода реверчена или прошла молча | **3** |
| доля выше 0.5 (по каждой из двух долей) | 2 |
| доля выше 0.2 (по каждой из двух долей) | 1 |

`0` — `Low`, `1–2` — `Medium`, `3` и больше — `High`.

**Honeypot весит втрое, потому что он единственный наблюдает ограничивающее *поведение* напрямую**, а
не прокси к нему. Остальные три косвенны.

**`Option` во всех четырёх полях содержателен.** `None` означает «проверить не смогли» и никогда не
сворачивается в `Some(false)`, которое читалось бы как «чисто». Конкретно: если каждый
протестированный держатель вернул `PrecompiledContractUnsupported`, `honeypot_reverted` остаётся
`None`.

Живой пример, зачем нужен композит: у одного жетона права минта **отозваны**, а проба перевода всё
равно реверчена с `exit_code: 714`. Однофакторная проверка объявила бы его чистым.

### 5.2 Контур Gift и NFT

`content.rs` — декодер TEP-64, написанный руками, потому что крейт, который дал бы готовый, его не
даёт; далее `gift_registry.rs`, `nft_authenticity.rs`, `domain_reputation.rs`,
`wallet_reputation.rs`.

Стартовый реестр Gift-коллекций держит **девять записей, помеченных как неисчерпывающие**, и CLI
печатает `NOT IN STARTER REGISTRY`, а не `FAKE`. Разница смысловая, а не стилистическая.

Настоящая находка при сборе этого реестра, которой не предполагало задание: все девять подтверждённых
коллекций делят **один** `code_hash` — код официального контракта Telegram Gift, отличный от
generic-коллекции площадки. Записано как второй, независимый и более дешёвый сигнал, усиливающий
адресную сверку, но не заменяющий её.

`domain_reputation` считает расстояние редактирования до известных легитимных доменов. Проверено
вживую: `fragm-ent.com` против `fragment.com`, расстояние 1. Честная оговорка лежит внутри: у одной
площадки нашлись **четыре** правдоподобных домена и ни одного авторитетного источника, какой из них
канонический, — все четыре внесены с флагом `multi_source_confirmed: false`.

## 6. Чего этот API не обещает

- **`sting lint` сам по себе не гейтит CI** — §2.2.
- **Ни одна из трёх командных строк не обещает стабильности интерфейса.** `version = "0.0.0"`,
  `publish = false`.
- **`ir_schema_version` — версия формата, а не обещание совместимости**: до публикации ломающие
  изменения разрешены без мажора.
- **HTTP-сервис не измерен на длинной дистанции.** Единственный нагрузочный прогон был локальным, на
  одной машине, а uptime так измерить нельзя.
- **Tolk через HTTP в контейнере не проверен вовсе** — в `vendor/` лежит только Windows-сборка
  компилятора, и Linux-бинаря для монтирования нет. Нативная пропускная способность Tolk замерена
  другой методикой и с числами HTTP один в один не сравнима.
